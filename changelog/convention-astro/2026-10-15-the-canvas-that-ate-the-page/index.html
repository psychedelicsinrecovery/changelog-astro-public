The canvas that ate the page - a debugging story with a headless browser

Medium 2026-10-15convention-astro 2 min readBy Christopher W
TL;DR: The Convention site looked "blank - only background" even with correct deploys. The culprit: the starfield canvas rendered as a static 900px-tall block ABOVE the page, pushing all content below the fold. Diagnosed with a headless browser, fixed with one CSS rule, verified the same way.
Read the full story →

🕵️ The symptom that lied

The page showed background and nothing else - through force refresh, incognito, everything. But the HTML had all the content, and every deploy succeeded. Two tempting wrong theories fell along the way: first a styling-token collision (real, but only made text hard to read), then a splash-screen gate (innocent).

🔬 Ground truth beats guessing

Instead of guessing again, the page was rendered in a headless browser and measured: the h1 was present, visible, fully opaque… at y = 1147px, 250 pixels below the viewport. Measuring the body’s children found the culprit instantly: #starfield-canvas, position static, 900px tall - the night sky was the first 900px of the document flow, and the whole page lived under the fold. The gallery never had this bug because its own style block fixes the canvas; the Convention’s styles were all scoped under .pir-conv, and the canvas sits outside that wrapper - so the fix never reached it.

The fix: convention-chrome.css - position: fixed for the canvas, plus unscoped rules for the header, footer and dock (they live outside the wrapper too). Verified the same way it was diagnosed: canvas fixed at zero, h1 in view, the full kit nav rendering, dock and footer in place, zero console errors.
